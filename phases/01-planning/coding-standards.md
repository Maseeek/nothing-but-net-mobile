# 25COB155 Coding Standards & Module Insights

This document synthesizes the coding practices, architectural patterns, and requirements extracted from the module lectures and coursework specification. All code generated by Antigravity must adhere to these standards.

## 1. Core Kotlin Practices
- **Immutability**: Favor `val` over `var` whenever possible.
- **Type Inference**: Use Kotlin's type inference; avoid explicit type declarations unless they add clarity or are required (e.g., public API).
- **Data Classes**: Use `data class` for models (e.g., `MessageRow`, `Movie`).
- **Conciseness**: Use lambda shorthand (`it`) for single parameters and trailing lambda syntax.
- **Null Safety**: Always use safe calls (`?.`) and Elvis operator (`?:`). Avoid the not-null assertion operator (`!!`) unless absolutely necessary for lifecycle reasons.

## 2. UI Development (Jetpack Compose)
- **Declarative UI**: Use Jetpack Compose exclusively for UI.
- **Scaffold**: Use `Scaffold` as the top-level structure for screens, including `topBar`, `bottomBar`, and `floatingActionButton`.
- **State Management**:
    - Use `remember { mutableStateOf(...) }` for local UI state.
    - Use `rememberSaveable` for state that must survive configuration changes (e.g., rotation).
    - **State Hoisting**: Hoist state to the lowest common ancestor to keep components stateless and reusable.
- **Units**: Use `dp` for dimensions and `sp` for font sizes.
- **Lists**: Use `LazyColumn` or `LazyGrid` for large or dynamic lists to ensure performance.
- **Adaptive Layouts**:
    - Use **Window Size Classes** to differentiate between Compact, Medium, and Expanded screens.
    - Implement adaptive navigation (e.g., Bottom Navigation for Compact, Navigation Rail for Medium).
- **Resources**: Reference strings, colors, and drawables via `R.string.*`, `R.color.*`, and `R.drawable.*`.

## 3. Architecture
- **Layered Architecture**: Clearly separate the **UI Layer** (Composables + ViewModel) from the **Data Layer** (Repository + Data Sources).
- **Uni-Directional Data Flow (UDF)**: Events flow from UI to ViewModel; state flows from ViewModel to UI.
- **ViewModel**:
    - Use `ViewModel` to encapsulate business logic and persist state across rotations.
    - Use `StateFlow` (preferred) or `LiveData` for observable state.
    - Use **Backing Properties**: `private val _uiState = MutableStateFlow(...)` and `val uiState = _uiState.asStateFlow()`.
- **Repository Pattern**: Use a Repository class to abstract data sources (Room, Retrofit, etc.) from the ViewModel.
- **Manual Dependency Injection**: Based on lecture slides, pass repositories to ViewModels manually (likely via a Factory if using standard `ViewModelProvider`).
    > [!CAUTION]
    > **Note on Hilt**: While Hilt is in the project dependencies, the CW spec says "Tools that automatically generate... dependency injection... are not allowed." We should verify if manual DI is preferred for marking purposes.

## 4. Data & Networking
- **Local Storage**: 
    - Use **Room** for structured, repeating data.
    - Use **Preference DataStore** for simple key-value pairs (settings).
- **Room Workflow**: Define `@Entity`, `@Dao` (with both suspend and sync methods for ContentProvider), and `@Database`.
- **Networking**: Use **Retrofit** for API calls and **Kotlinx Serialization** for JSON parsing.
- **Coroutines**: Perform all long-running tasks (IO, Network) on background threads using `viewModelScope` and `Dispatchers.IO`.

## 5. Coursework Specific Requirements (Mandatory)
- **Screens**: Minimum of two distinct screens.
- **Navigation**: Use the **Navigation Component** (NavHost, NavController) with routes defined in an `enum class`.
- **Intents**: Use **Explicit Intents** to move to outside apps (e.g., Browser, Maps).
- **Lifecycle**: Ensure the app handles orientation changes correctly (persisting state).
- **Permissions**: Declare in Manifest; request **Runtime Permissions** for dangerous actions in-context with rationale.
- **ContentProvider**: Create a custom `ContentProvider` to share data. Implement a **Data Contract** and use **UriMatcher**.
- **Testing**: Implement **Instrumented Tests** for the `ContentProvider` (in `androidTest/java`).

## 6. Performance & Security
- **Performance**: Use **Logcat** for debugging. Avoid work on the Main Thread. Use **Profiler** and **Macrobenchmark** for measurement.
- **Security**: Minimise data collection. Always use **HTTPS**. Avoid hardcoding API keys. Use **Android Keystore** for sensitive info.

## 7. Style & Aesthetics
- **Authenticity**: Code should be clean and readable, reflecting the "university student" level—elegant but not overly engineered.
- **Material 3**: Follow Material Design 3 guidelines (M3 components like `TopAppBar`, `NavigationBar`, etc.).
